# 아이디어를 스펙으로 발전시키기

## 개요

자연스러운 협업 대화를 통해 아이디어를 완성된 스펙 문서로 발전시킨다.

현재 프로젝트 컨텍스트를 파악한 뒤, 한 번에 하나씩 질문하여 아이디어를 구체화한다. 무엇을 만들지 파악이 되면, 200~300단어 섹션 단위로 스펙을 작성하며 각 섹션마다 방향이 맞는지 확인한다.

## 프로세스

**아이디어 파악:**
- 먼저 현재 프로젝트 상태를 확인한다 (파일, 문서, 최근 커밋)
- 한 번에 하나씩 질문하여 아이디어를 구체화한다
- 가능하면 객관식 질문을 선호하되, 개방형 질문도 무방하다
- 메시지당 질문 하나 — 더 탐색이 필요한 주제는 여러 질문으로 나눈다
- 파악에 집중: 목적, 제약, 성공 기준

**접근방식 탐색:**
- 방향이 아직 불명확할 때 2~3가지 접근방식을 트레이드오프와 함께 제안한다
- 사용자가 이미 방향을 제시한 경우, 대안을 강요하지 않고 그 방향을 검증한다
- 추천과 근거를 포함하여 대화체로 선택지를 제시한다
- 추천 방식을 먼저 제시하고 이유를 설명한다

**스펙 제시:**
- 무엇을 만들지 파악이 되면 스펙을 작성한다
- 200~300단어 섹션 단위로 나눠 작성한다
- 각 섹션마다 방향이 맞는지 확인한다
- 아래 출력 형식의 표준 섹션을 다룬다
- 이해가 안 되는 부분이 있으면 돌아가서 명확히 한다

## 출력 형식

완성된 스펙을 대화 안에서 인라인으로 제시하고, 완료를 알린다:

> 스펙 초안이 완성되었습니다. /dev:spec이 파일로 저장합니다.

### 필수 섹션 (모든 토픽 유형)

```markdown
# <기능명> 스펙

**상태**: Draft
**작성일**: YYYY-MM-DD
**작성자**: @<username>

> **문서 범위**: 이 문서가 다루는 범위

## 1. 개요
### 1.1 배경
### 1.2 목적

## 2. 목표

## 4. 의사결정

| 항목 | 결정 | 근거 |
|------|------|------|

## 5. 범위 밖 (Non-goals)

## 6. Open Questions

## 7. 관련 문서
```

### 선택 섹션 (토픽 유형에 따라 포함)

| 섹션 | 코드/기능 | 워크플로우/정책 | 역할/구조 |
|------|----------|----------------|----------|
| `## 3. 아키텍처` (전체 구조, 주요 컴포넌트) | ✅ 포함 | ⬜ 해당 없으면 생략 | ⬜ 해당 없으면 생략 |
| `## 3. 역할 정의` (역할 경계, 책임 분리) | ⬜ 해당 없으면 생략 | ✅ 포함 | ✅ 포함 |

해당하는 선택 섹션에 `## 3.` 번호를 사용한다. 토픽이 어느 유형에도 명확히 해당하지 않으면 `역할 정의` 구조를 사용하여 경계와 책임을 기술한다 — 섹션 3은 어떤 형태로든 반드시 포함된다.

## 핵심 원칙

- **한 번에 하나씩 질문** — 여러 질문으로 압도하지 않는다
- **객관식 선호** — 가능하면 개방형보다 객관식이 답하기 쉽다
- **YAGNI 철저히** — 불필요한 기능은 모든 설계에서 제거한다
- **대안 탐색** — 방향이 불명확할 때 2~3가지 접근방식을 제안한다. 사용자가 방향을 제시한 경우 대안을 강요하지 않고 검증한다.
- **점진적 검증** — 섹션 단위로 스펙을 제시하고 각각 검증한다
- **유연하게** — 이해가 안 되는 부분이 있으면 돌아가서 명확히 한다
- **미결 사항 표시** — 결정되지 않은 사항은 Open Questions에 기록하고, 답을 지어내지 않는다
