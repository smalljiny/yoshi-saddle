# brainstorming 스킬과 /dev:spec 계약

> brainstorming 스킬과 `/dev:spec` 명령어 사이의 역할 경계, 출력 계약, 동작 규칙을 기술한다.

## 개요

스펙 작성 흐름은 두 구성 요소가 협력한다. brainstorming 스킬은 대화를 통해 스펙 내용을 완성하고, `/dev:spec`은 파일 저장과 Codex 리뷰 루프를 담당한다.

## 역할 분리

| 역할 | 담당 |
|------|------|
| 대화로 스펙 내용 완성 | brainstorming 스킬 |
| 완성된 스펙 파일 저장 | `/dev:spec` |
| Codex 리뷰 루프 관리 | `/dev:spec` |
| dev-context.json 접근 | 없음 (양쪽 모두 접근하지 않음) |

## brainstorming 스킬 동작

**대화 프로세스**:
- 한 번에 하나씩 질문하여 아이디어를 구체화한다
- 방향이 불명확할 때만 2-3가지 접근방식을 제안한다. 사용자가 이미 방향을 제시한 경우 대안을 강요하지 않고 검증한다
- 200-300단어 섹션 단위로 스펙을 작성하며 각 섹션마다 검증한다

**출력 계약**:
- 완성된 스펙을 대화 안에서 인라인으로 제시한다
- 파일로 저장하지 않는다
- 완료 시 자연어로 선언한다: *"스펙 초안이 완성되었습니다. /dev:spec이 파일로 저장합니다."*

**출력 형식**:

필수 섹션 (모든 토픽 유형):
```
개요 / 목표 / 의사결정 / Non-goals / Open Questions / 관련 문서
```

선택 섹션 (토픽 유형에 따라):
- `## 3. 아키텍처` — 코드/기능 토픽
- `## 3. 역할 정의` — 워크플로우/정책/역할 조정 토픽
- 어느 유형에도 해당하지 않으면 `역할 정의` 구조를 사용한다. 섹션 3은 항상 포함된다.

## /dev:spec 동작

**파일 저장**: brainstorming이 완료를 선언하면 스펙을 `docs/_local/backlog/<topic>/spec.md`에 저장한다.

**Codex 리뷰 루프**: 저장 후 사용자에게 Codex 리뷰 실행을 안내한다. 리뷰 결과가 `READY` 또는 `READY WITH NOTE`가 될 때까지 반복한다.

**Notes 반영 기준**: 사실 오류, 누락된 컨텍스트, 또는 리뷰에서 식별된 누락 Open Questions를 수정하는 Notes만 반영한다. 문체 선호나 범위 확장 Notes는 반영하지 않는다.

**분할 처리**: 분할 시 부모 디렉토리를 `docs/_local/backlog-split/<topic>/`으로 이동하여 `/dev:plan` 탐색에서 제외한다.

## spec-review 체크리스트 계약

체크리스트 항목 3 (아키텍처 충분성)은 코드 토픽의 `아키텍처` 섹션과 비코드 토픽의 `역할 정의` 등 동등한 구조를 모두 수용한다. 어떤 형태로든 섹션 3이 없으면 FAIL이다.

## 제약사항

- brainstorming 스킬은 dev-context.json을 읽거나 쓰지 않는다
- `/dev:spec`은 dev-context.json을 읽거나 쓰지 않는다. 등록은 `/dev:plan`이 처리한다
- Codex를 Claude Code가 직접 호출할 수 없다. 사용자가 `codex` 명령을 수동으로 실행한다
